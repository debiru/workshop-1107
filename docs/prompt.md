# アイデア

## 【1. ドメイン名の信頼性、フィッシング対策】

ホモグラフ攻撃（目視で正規のドメイン名と誤解させて仕掛けるフィッシング）のサイトにアクセスしたときに、それを検知するためのツール。ブラウザの閲覧履歴かlocalStorageか何かを照合して、初めてアクセスするドメイン名であれば警告を出すとか。

## 【2. localStorage 自動保存フォーム】

よくWebフォームに長文を入力して送信しようとしたときに、ブラウザが予期せずクラッシュしたりサイト側でセッションタイムアウトが起きて、入力内容が失われることがある。それを防ぐためにブラウザ拡張側で、Webフォームに入力した内容を自動保存して復元できるようにする。

## 【3. Chrome以外では閲覧できないサイト】

Web標準を理解できないクソサイトがGoogle Chrome以外ではサービス利用できないようにしていることがある。Firefoxなど締め出されているブラウザでそうしたサイトに遭遇したときに、余計な注意書きやUAブロッキングを回避できるようにする。

## 【4. HTML設計可視化】

最近はReactやSPAで作っているサイトが多いけれど、フロントエンド設計がクソなことが多くて、まあSPAに限らないけれどWordPressとかなんでもいいけど、HTML設計が洗練されていないサイトが多いので、アクセスしたサイトのHTML設計がどうなっているのかを解析・分類・Prettyソースコード出力などを行えるツール。

# 作成したいもの

Google Chrome 用のブラウザ拡張機能を作るというワークショップです。

## 私が作るブラウザ拡張機能

今回は、アクセスしたWebページに存在するHTMLフォームのうち、テキスト入力をするもの（つまり `<input type="text">` と `<textarea>` 要素）について、そこに入力した文字列をブラウザ拡張側で自動保存して、ユーザーがHTMLフォームをフォーカスかクリックか何かをしたときに、自動保存した内容を呼び出せるようにする機能を作ろうと考えています。

この機能の目的は、Webページ上でテキスト入力フォームに多くの項目や長文を入力したにもかかわらず、ブラウザがクラッシュしたり、Webサイト側でセッションタイムアウトするなどして、結果的に入力した多くのテキスト情報が失われることがあり、そうした被害を防ぐための機能を提供するものです。

## 詳細な機能仕様案

- 一連のフォームデータは、Webページ（URL）ごとに管理します。
- Webページ側のフォームコントロールと、保存するフォームデータの対応付けは直接的には行いません。
    - これはどういう意味かと言うと、ある時点でWebページに `<textarea name="contact-body">` のような要素があり、その内容を拡張機能で保存したとして、後にWebページ側のHTML設計が変わり `<textarea name="inquiry-body">` のようになった場合でも、保存していたデータを新しいフォームコントロール側に呼び出せるようにしたいため、保存するデータの id として `name="contact-body"` 情報を用いてその id 情報を使ってWebページ側のフォームコントロールと自動的に直接関連付けるといった処理は行わないという意味です。
    - Webページ側のフォームコントロールの存在と、保存したデータは独立したリストアイテムとして扱い、例えば `<textarea name="inquiry-body">` をフォーカスしたときに、そのページの保存データがあれば「自動保存された内容で入力値を復元しますか」といったプロンプトを出して、どの保存データを呼び出すかはユーザーが自分で選択するといった方式を考えています。
- 前述の話を更に改良して、そもそもフォームコントロール1個ずつに対してユーザーが操作を行うのではなく、保存データの一覧に対して、フォームコントロールをユーザーが手動で関連付けるUIを提供し、その関連付けに基づいて入力内容を復元するかどうかを一括処理できるようにしようかと考えました。
    - Webページ側のフォームコントロールと、保存したデータの関連付けやデータの呼び出し方法についてはよりよい設計を検討する余地がありそうです。
- 自動保存するテキストデータは、最終入力値だけではなく、過去の何世代かの内容を保持したいです。ユーザーが長文を入力していたのに、誤操作か何かで一度全テキストを削除したとして、その結果が保存されてしまった場合、もともとも長文が失われてしまうのを防ぐためです。
    - これについても、データ保全性と利便性を考慮したよりよい設計の余地がありそうです。
    - 最終入力時点のデータの他に、3分なり5分なりごとの自動保存データがあるとよいのかなと思いますが、その数分ごとの自動保存を何世代まで保持するのか、単純に時間経過ごとに世代を増やすのかそれともテキストデータに一定量以上の変更点がある場合にのみ世代を増やすのかといったことも検討の余地がありそうです。
- 保存・復元可能とするフォームコントロールの種類をどうするのかについても検討の余地があります。
    - 対象要素案1： `<input type="text">` と `<textarea>` 要素だけとする。
    - 対象要素案2：対象要素案1に加え、`<input type="email">` などテキスト入力候補のもの。ただし `<input type="password">` は除外する。
    - 対象要素案3：対象要素案2に加え、`<input type="range">` や `<input type="checkbox">` など、`type="password"` 以外の全てのフォームコントロールを対象にする。これは、一つのテキスト入力エリアが長文の場合というよりも、多くのフォームコントロールがあるようなフォームにおいて、入力内容の復元をしたいケースをサポートするものである。

# 調整項目について

## (1) 対象コントロールの範囲
> 僕の案：案2（テキスト系＋textarea、password除外）。案1に絞るか、案3まで広げるか

案2でよいと思います。案3はニーズがそこまで高くないためです。何なら案1でもいいですが。

## (2) 復元方式
> 僕の案：フォーカス時のパネルで個別復元 ＋ 手動対応付けで一括復元、の両方

フォームコントロールのフォーカスごとに操作するのはやめようと思います。

デバッグツールバーのようなものを表示して、そのエリアで操作を行い、元のページ内にあるフォームコントロールと、復元したいデータを手動で紐づけて、それに対して自動入力（テキスト復元処理）を実行するというボタンを押すことでデータがセットされるといった方法にしようと考えています。

## (3) 世代管理
> 僕の案：3分＋10文字以上の変化でスナップショット、急減時は直前を緊急保存、最大10世代

ストレージ容量がどのくらいまで許容されるか分かりませんが、容量的に問題がないのであればページごとに30世代なり100世代になり、そのくらいまで大きくしたい気持ちもあります。

## (4) ページの区切り方
> 僕の案：origin＋パス名（クエリ除外）。URL丸ごとにするか、ドメイン単位にするか

URLベースにしようと考えていますが、まずハッシュフラグメントは無視してよいです。

ただし、クエリパラメータは重要です。クエリパラメータによってページを分けているサイトも多いので、クエリパラメータはページIDとして含めたいと考えています。ただ、パラメータの中には同じページなのに異なるパラメータが与えられることも多いとは思うので、データの呼び出し時に、異なる「ページID」として保存されたデータも呼び出せるような仕組みにしようとかと考えています。

## (5) 保存データの保持期間・上限
> 僕の案では未設定だった点。自動削除するか、手動削除のみにするか

世代管理の話と重複しますが、非常に古い保存データは自動削除（自動ローテート）でいいと思います。また、ユーザーが明らかに不要だと考える入力データは手動削除ができるようにしてもよいと思います。

## (6) 名称・説明文
> 僕の案：「フォームレスキュー」

もう少しおしゃれな印象にしたいので「PhoenixField」にします。

## (7) UIの見た目
> ポップアップ／ページ内パネル／設定画面の構成

復元方式にも書きましたが、ポップアップやモーダルは避けたいです。HTMLのdetails要素のような形で開閉する分には問題ないので、ページ内パネルを前提に操作エリアは提供したいです。設定画面の構成は特にこれといった指定はありません。
